# DeepInfer: independent source review

Author: numerical_source_audit  
Date: 2026-10-21  
Parent: execution-fabric research; coordinator owns reconciliation

DeepInfer offers useful execution techniques, but adopting its runtime would not establish Qwen/Gemma support or preserve our numerical contracts. The immediate candidates **after vLLM parity** are bounded launch reuse, reduced synchronization, and fusion that preserves the already established arithmetic. Trained speculation is a separate, potentially substantial Qwen/Gemma opportunity. Wide expert parallelism and DeepSeek-specific cache reconstruction belong later.

This is source/document research. No DeepInfer build, kernel, model, benchmark, SDK, container, or hardware qualification was performed. No live implementation or shared plan was edited. All benefit rankings below are engineering inferences, not measured Zerogravity speedups.

## What executes

The public path is an offline Python `LLM` wrapper around an iteration scheduler, a PyTorch model runner and one worker per accelerator. Scheduler, sequence/block management and metadata preparation use a C++ extension; model operators dispatch to specialized vendor libraries and TileLang kernels. `setup.py` builds concrete C++ engine/utility extensions rather than compiling a generic mathematical graph. [LLM wrapper](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/entrypoints/llm.py), [extension build](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/setup.py), [worker](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/worker.py#L81-L173).

Backend selection is centralized for TileLang factories, with separate CUDA and Ascend implementations. Ascend adapts the Torch CUDA-facing interface to NPU operations, uses HCCL and different scale packing; this is real backend-specific code, not proof that the same compiled arithmetic is portable. [Dispatcher](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/tilelang_ops/ops.py), [platform implementation](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/platform.py).

## Implemented execution mechanisms and transfer conditions

### 1. CPU/GPU overlap and device-side feedback

The common step executes current forward, processes the previous result, samples the current result, then defers current postprocessing for overlapping decode. Sampling completion events are synchronized before CPU postprocessing; variable-length metadata corrected on GPU has an explicit D2H event before CPU consumption. New requests receive fresh CPU inputs, while overlapping requests reuse previous GPU sampled/draft outputs through remapping. This is an actual producer pipeline, not speculative use of uncompleted CPU token metadata. [Worker step and correction](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/worker.py#L104-L248), [ZOS metadata and input transport](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py#L34-L121).

Deferred metadata/output pools and cloned cache references are retained until a later release point; clone references wait for their recorded event. This is useful evidence that asynchronous scheduling still needs explicit ownership and completion. [DeferredRelease](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/engine/llm_engine.py#L64-L111).

**Application:** after parity, measure CPU bubbles at real concurrent short-context serving. Reuse the existing actor/fair worker and original completion-bound token transport. Schedule CPU preparation ahead; do not publish a future StateRoot or expose an uncompleted packet. Cancellation must retain every genuinely submitted owner and invalidate stale work.

### 2. Stable buffers, graph replay and launch dependencies

CUDA graph capture preallocates maximum metadata and output storage, takes smaller views, captures largest-to-smallest and shares the graph memory pool. Shapes use powers of two for small batches, then configurable fixed intervals. Runtime selects the smallest recorded graph covering the submitted token count; requests outside the maximum refuse. Prompt processing stays outside this decode-graph route. [Graph runner](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/cuda_graph_runner.py#L35-L150), [model-runner selection](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/model_runner.py#L156-L182).

Runtime also enables programmatic dependent launch in DeepGEMM and TileKernels. CUDA norm kernels contain producer/consumer PDL synchronization and triggers. This is distinct from full-model graph replay or algebraic fusion. [Runtime setup](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/runtime_config.py#L48-L62), [CUDA norm](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/tilelang_ops/cuda/norm.py#L213-L285).

**Application:** high priority if actual launch overhead dominates small Qwen/Gemma decode. First retain stable allocations and parameter buffers within the original service; only then consider a closed replay mechanism with exact lease/generation, padding, initialized-range, cancellation and completion rules. SM100 PDL code is not a portable SM86/Renoir optimization.

### 3. Fusion and physical layouts

The attention path can fuse normalization, RoPE, attention, output RoPE and FP8 casting. Selection checks backend, attention head count and packed/sparse phase. Linear output allocations enforce 32-byte row alignment; FP8 data/scales use prescribed layouts. [Attention backend](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/attention_backend.py#L23-L135), [selection conditions](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/attn.py#L61-L110), [linear allocation](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/linear.py#L76-L151).

The CUDA norm explicitly adds residuals into an **input-dtype fragment**, then widens that rounded sum for statistics; it may emit normalized BF16 and quantized outputs/scales together. That differs from our accepted vLLM unrounded-F32 residual sum. A name such as `RMSNorm` does not make the implementations interchangeable. [Exact add/cast/reduction/store sequence](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/tilelang_ops/cuda/norm.py#L216-L280).

mHC carries deferred mixing coefficients across neighboring sublayers to combine post/pre work; Engram precomputes invariant fused weights. Both operate on trained DeepSeek architecture components. The general opportunity is eliminating invariant work and redundant tensor traffic, not adding mHC/Engram to an unrelated checkpoint. [mHC lazy path](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/hc.py#L47-L90), [Engram runtime](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/engram.py#L93-L142).

**Application:** fuse the highest traffic adjacent operations only after retaining reference rounding, reduction and store boundaries. Keep explicit physical BF16/F32 layout and original operand provenance. Qualify full layer/state/fullV again after fusion; isolated cosine agreement is insufficient.

### 4. Distributed topology and communication

Code constructs attention DP, balanced CP, expert-parallel and Engram process groups. CP uses session-bounded all-gather buffers whose output aliases reused storage. Mega-MoE is selected only within the checked scale-up/NVLink domain. These are multiple parallel decompositions, not a generic pipeline-parallel stage compiler. [Groups](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/parallel_utils/parallel_state.py#L63-L122), [CP storage lifetime](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/parallel_utils/cp.py), [MoE selection](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/mlp.py#L163-L187).

The unfused expert path overlaps dispatch/combine with compute, reserves communication SMs, and computes shared experts while routed work proceeds. The fused route combines expert work and optionally shared experts in Mega-MoE, with `fast_math=True`. Model-wide symmetric buffers can share a largest backing allocation and cache immutable views. [Dispatch/combine/Mega-MoE](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/mlp.py#L423-L569), [shared communication buffers](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/parallel_utils/userbuffer.py#L172-L223).

**Application:** distributed work is later than single-device Qwen/Gemma parity and real serving measurements. Reuse topology-aware placement, bounded shared transport and overlapped independent work when hardware/model demands it. Do not copy an EP64 configuration into a dense single-GPU workload.

### 5. Expert placement and load balancing

The policy assigns extra physical replicas to hot logical experts, then greedily places replicas to reduce historical peak rank load; logical-to-physical mappings remain explicit. Actual weight shuffling uses buffered batched P2P or intranode IPC/symmetric memory. This trades resident weight memory and rearrangement bandwidth for less rank imbalance. [Placement algorithm](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/eplb/policy.py), [weight movement](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/eplb/shuffle.py).

**Application:** conditional on a specifically selected MoE Qwen/Gemma model and enough accelerators. Preserve immutable logical source identities while admitting independently owned physical replicas; never mutate a published source descriptor to represent the latest placement. Dense .8B/2B models receive no expert-replication benefit.

### 6. Cache layouts, prefix sharing and bounded replay

There is an implemented paged block allocator with reference counts, state slots and clone/fork paths. Cache geometry comes from trained attention configuration, with SWA rings, compression state, paged compressed KV, index KV and cross-layer sharing. Exact formats include E4M3/UE8M0 per 32 main/SWA storage; optional E2M1/E4M3 per 16 main KV; E2M1/UE8M0 per 32 index KV. These are different byte layouts, not a single generic “FP4 cache.” [Block ownership](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/csrc/engine/block_manager.hpp), [cache layout](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/cache_engine.py#L527-L584), [format definitions](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/tilelang_ops/cache_common.py#L98-L150).

Cross-layer sharing validates source/consumer maps and rejects consumers without matching source configuration. YOCO compaction removes selected suffix queries, remaps hidden/residual/index state and invalidates derived caches at the boundary. [Sharing validation](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/cross_layer.py#L20-L106), [compaction](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/yoco.py#L46-L110).

The deployment Q&A explicitly calls bounded SWA replay **approximate**: it reconstructs a suffix with truncated visibility rather than the full model's complete dependency history. The mask/compact comparison tests establish equivalence between two implementations of that same truncated visibility, not equivalence to untruncated attention. It is not an exact-parity optimization for our current Qwen state. [Replay description](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/doc/inference_deployment_qa.md#L148-L158), [comparison contract](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/examples/yoco/README.md), [shared visibility metadata](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/input_metadata/yoco.py#L1-L5).

**Application:** exact prefix reuse and bounded scratch reuse are relevant; importing YOCO, learned compression, sparse token selection or approximation into Qwen/Gemma requires a matching trained model or a separately authorized numerical profile. Quantized state needs its own source/layout/quality and full-state tests. Do not put approximate replay under the accepted vLLM profile.

### 7. DSpark and adaptive verification

The actual drafter consumes selected target hidden features, shares embedding/head, generates a parallel draft block, then sequentially adds a learned low-rank Markov transition bias. A learned confidence head emits per-position acceptance estimates. It needs compatible trained weights and feature-layer configuration. [DFlash/DSpark runtime](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/mtp/dflash.py#L126-L170), [sequential draft sampling](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/mtp/dflash.py#L254-L316).

C++ chooses verification capacity from a recorded hardware cost curve plus runtime estimates. It explicitly separates N−2 confidence used for capacity selection from newer confidence used for request allocation, checking schedule/process counters. GPU allocation uses cumulative prefix survival, stable ranking and remapping. Copying only the global top-k idea would omit its causality conditions. [Capacity scheduler](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/csrc/engine/mtp_varlen.hpp#L135-L234), [GPU allocation reference/tests](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/tilelang_ops/schedule_mtp_varlen.py#L31-L124).

The cost-cache key includes model name, batch sizes and DP/CP/EP sizes, but not an immutable model-content/kernel/device identity. Its TTL and runtime correction are useful operational mechanisms; a Zerogravity profile cache should additionally bind the actual source and provider/hardware contract. [Cost-cache key](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/decode_perf_cache.py#L24-L49).

DeepSpec independently publishes DSpark/Eagle3/DFlash training configurations and checkpoint links for **Qwen3-4B/8B/14B and Gemma4-12B-it**. Its default target-cache example is approximately 38 TB and its default training setup is 8 GPUs; this is not a free runtime switch. Checkpoints are target- and training-mode-specific; the authors recommend retuning for domains/thinking mode. [DeepSpec primary README](https://github.com/deepseek-ai/DeepSpec/blob/005e03b81cec38b7da6399833d609ee89a2587f2/README.md#released-checkpoints).

**Application:** promising later for larger compatible Qwen/Gemma targets once exact target verification, rollback and real serving work. No checkpoint in this review proves compatibility with current Qwen3.5 .8B/2B or queued27B. Do not acquire/train anything from this research. A draft can use the same mathematical engine with independent state owners; the target remains the acceptance authority.

### 8. Sampling, reproducibility and grammar work

Sampling fuses temperature/filtering/log-normalization, fixed-point probability accumulation and rejection handling; sequence seeds and positions provide reproducibility. The shipped sampler deliberately uses `DRAFT_PROB_PENALTY=5e-5` in residual weights. Its own comment derives a nonzero distribution-error bound; the CUDA implementation applies the penalty. This is **not** a blanket exact-target-distribution or bitwise parity guarantee. [Documented bound](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/tilelang_ops/common.py#L1-L18), [constant](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/tilelang_ops/common.py#L45-L48), [actual residual computation](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/tilelang_ops/cuda/fused_sample.py#L413-L474), [fixed-point selection](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/tilelang_ops/cuda/random_sampling.py#L7-L46).

Batch invariance enables deterministic algorithms and special reduction choices; it is NVIDIA-only and runtime explicitly rejects it on Ascend. The test compares batched versus single-request token/logprob/top-k results using a forced trajectory. That is useful reproducibility coverage, not all-layer/full-state bitwise equivalence to another engine. [Runtime guard](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/runtime_config.py#L54-L62), [test](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/tests/models/test_batch_invariant.py#L45-L93).

Grammar compilation uses a CPU thread pool and pending futures, then main-thread admission; runtime token masks feed the sampler. This can reduce GPU-path stalls without changing model equations, but compiler/matcher state and cancellation still need ownership. [Builder/admission](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/structure_output/so_matcher_builder.py#L17-L124), [sampler interface](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/layers/sampler.py#L56-L99).

**Application:** preserve our current greedy tie/status/output contract; later separately qualify seed/RNG/filter/rejection semantics and grammar tokenization. Reproducible approximated sampling is not the same claim as exact vLLM arithmetic.

## Prefill/decode scheduling and resource differences

Local prefill is FIFO with token/context/CP-alignment and cache-admission constraints, including chunked-prefill bookkeeping. Decode sorts active requests and may stop or recompute preempted work; structured-output preemption currently stops rather than recomputes. This is a request scheduling policy, not a fairness guarantee across models/providers. [Prefill admission](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/csrc/engine/scheduler.hpp#L318-L500), [decode/preemption](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/csrc/engine/scheduler.hpp#L509-L578), [preemption semantics](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/csrc/engine/scheduler.hpp#L700-L723).

Worker memory sizing profiles a model run, includes observed non-Torch allocations, reserves state space and derives a KV capacity from a utilization fraction. The pinned code averages rank capacities. This differs from reserving every process-shared provider envelope before work. NUMA CPU/memory binding and reusable pinned buffers reduce host transfer overhead, but neither establishes a physical memory admission authority. [Capacity calculation](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/base.py#L194-L247), [NUMA binding](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deep_cluster/topology/bind.py#L74-L94).

The deployment document describes dedicated storage, wide-EP decode, stage disaggregation, quota-based load balancing, asynchronous cache transfer and request rerouting. It says TP/CP are not currently used in that production configuration. The global KV/load-balancing components are not fully released, so they are descriptions rather than directly reproducible code in this tree. [Production boundaries and configuration](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/doc/inference_deployment_qa.md#L16-L57).

## Open proposals and concrete audit cautions

- **PR35 is open/unmerged:** proposes minimum capacity across ranks, full decode block-deficit reservations and cleanup of terminated waiting references. Pinned `base.py243–245` really uses rank averaging; scheduler `_append_slot` allocates a single missing block then checks exact size. These are concrete review targets, but this research did not execute a reproduction or validate the proposed patch. [PR35](https://github.com/deepseek-ai/DeepInfer/pull/35), [current append](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/csrc/engine/scheduler.hpp#L748-L759).
- **PR34 is open/unmerged:** pinned `SamplingParams` turns temperature0 into1e-5 with top-k disabled. The proposal supplies a close-logit example showing this is not true greedy normalization. Do not import that behavior into our accepted lowest-ID greedy contract. [Current normalization](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/sampling_params.py#L71-L79), [PR34](https://github.com/deepseek-ai/DeepInfer/pull/34).
- **SM90 is a draft RFC**, not current support: its author describes missing FP4 hardware/attention support and proposes later implementation. No SM86/AMD support follows from the existing platform abstraction. [PR47](https://github.com/deepseek-ai/DeepInfer/pull/47).

## Fit with the existing Zerogravity engine

This comparison is based on current isolated source, not historical descriptions. The SourceIdentity is a process-local issuer, not itself a checksum; verified source artifacts and retained owners supply content provenance. `SessionAuthority` owns publication and epochs; physical completion and state leases remain separate. The ResourceArbiter is process-local, not an OS-wide free-VRAM meter. Preserve these exact limitations.

| Concern | DeepInfer evidence | Required composition here |
|---|---|---|
| Mathematical execution | Python model traversal + concrete vendor/TileLang operators | Lower qualified kernels through the existing mathematical plan, original resident actor and node traversal; no second Python/model engine. |
| Source ownership | HF configuration/loading followed by weight repacking, layout conversion and freeing original tensor storage | Retain authenticated source owner; packed physical layouts are derived buffers with explicit ordered members and independent charges, never a source retag. |
| State | Mutable sequences, block/state reference counts, clone/fork and optimistic speculative advance | Candidate state stays independent from immutable current StateRoot; only original Session commit advances the root after trusted completion and required validation. |
| Memory | Profiling/utilization-derived cache capacity; reusable global communication buffers | Keep actual host/device/native/transfer admissions under the same process-shared physical authority, including graph pools, provider internals and pending work. |
| Scheduling | Request-level FIFO/chunk/decode/speculation policy | Reuse policy ideas inside fair model/provider workers; preserve bounded waiting and cancellation across workloads. |
| Completion | Explicit stream/event ordering and delayed pool release | Keep original initialized-range certification, actual completion, source/state/output ownership and quarantine. A future scheduled batch is not Ready. |
| Failure | Distributed barriers and explicit worker/process cleanup; production rerouting described separately | Unknown completion fences the original service and retains its actual graph; cancellation cannot force unload or reclaim uncertain resources. |

Local primary paths inspected: `crates/zerogravity-core/src/{accelerator.rs,state.rs,session_root.rs,resource_arbiter.rs}` and `crates/zerogravity-gpu/src/{physical_service.rs,resident_leases.rs,resident_inference.rs}` in the isolated tree. Relevant DeepInfer counterparts are the linked loader/worker/block-manager/scheduler/userbuffer code above. No absence claim is intended for files not reviewed.

## Proposed order after vLLM parity

These are recommendations for coordinator reconciliation, not an implementation queue change.

| Priority | Candidate | Qwen/Gemma relevance | First meaningful acceptance/performance gate |
|---|---|---|---|
|1 | Stable reusable buffers and launch batching/replay | Broad; especially small decode where launch overhead is measurable | Same source/fullV/all state, natural feedback and cancellation first; then concurrent short-context TTFT/TBT and actual emitted-token goodput, with cold/setup costs separate. |
|2 | CPU scheduling/metadata overlap with device producer feedback | Broad; avoid idle gaps while retaining fair scheduling | Real ready-packet→next-input transport, stale epoch/cancel tests, unknown completion, bounded in-flight ownership; compare overlap on/off at identical output and load. |
|3 | Exact adjacent fusion and fewer memory round trips | Broad; norm/activation/rotary/cache-store depend on architecture | Stage-by-stage exact arithmetic including F32/BF16 stores and source casts; full connected state/fullV after change; capture actual bandwidth/launch bottleneck. |
|4 | Exact prefix reuse, chunk sizing and NUMA locality | Broad with repeated/long prompts; model-specific state schema still required | Source/config/profile keyed prefix identity, restore/fork/cancel, all active state, actual transferred bytes and memory peaks; no approximate replay under exact profile. |
|5 | Compatible trained DSpark/DFlash/Eagle speculation with adaptive budgets | Direct research artifacts for some Qwen3/Gemma4 targets; no current .8B/2B/27B compatibility established | Independent draft source/state; exact target verification/rollback, RNG and selection-causality tests; real accepted emitted-token goodput at low/high concurrency. |
|6 | Quantized W/activations/KV and specialized vendor kernels | Hardware- and model-dependent; new numerical profile required | Actual source/config support and tensor format; independent quality/state comparisons plus physical memory; no BF16-profile relabeling. |
|Later | Expert replication/EP, distributed P/D, storage tiers, sparse/YOCO/Engram/mHC | Only selected compatible models/hardware; largely DeepSeek-specific here | First demonstrate workload/topology need and release availability; independently qualify each model/precision/geometry and recovery path. |

The common composable lesson is to separate **immutable numerical/kernel contracts**, **source-derived physical layouts**, **request/state ownership**, and **scheduling choices**, so scheduling can improve without silently changing arithmetic or authority. DeepInfer supplies concrete examples of this separation's performance value and of the boundaries that remain model-, hardware- or approximation-specific.
