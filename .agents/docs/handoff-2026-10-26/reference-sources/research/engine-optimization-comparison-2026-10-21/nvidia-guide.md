# NVIDIA DeepSeek V4 / two-Spark recipe: independent research

Author: rotary_native_audit. Inspected: 2026-10-21. Parent: ROOT execution-fabric investigation.

Scope: the supplied NVIDIA forum guide, its accessible source, and primary upstream/model documentation. Research and proposed design only. No builds, model/SDK/executable downloads, GPU work, benchmarks, system changes or implementation. No DeepInfer reconciliation is included; ROOT receives this report independently.

## Findings and priority

The recipe combines model-specific low-precision sparse attention and MoE kernels with ordinary serving mechanisms: tensor parallelism, bounded token scheduling, prefix caching, graph replay and speculative verification. The inspected launch scripts expose those choices directly. It is not evidence that a generic dense model acquires million-token efficiency merely by changing a context flag. [1M launch](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/launch/serve-1m.sh), [256K launch](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/launch/serve-256k.sh).

Recommendation, conditional on completed vLLM parity: prioritize Qwen and Gemma4 execution efficiency, with measured batching/launch overhead and source-bound layer-specific cache policy first. Evaluate trained MTP immediately afterward where low-concurrency decode dominates. DeepSeek's learned compression, its SM12x kernels and multi-Spark transport are separate later projects. These are engineering priorities inferred below, not measured Zerogravity speedups.

## Why the model and two GB10 systems make this feasible

### Compute and weight residency

DeepSeek-V4-Flash is a 284B-total / 13B-active MoE. Only selected experts compute each token, while inactive experts still require storage or an explicit offload plan. Therefore active parameter count explains some compute economics, not total memory residency. [Official model card](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash).

The current official config sets 43 layers, 256 routed experts, 6 selected plus a shared expert, and `expert_dtype: fp4`, alongside FP8 quantization metadata and BF16 tensor defaults. The guide's broad “FP8” label must not be read as one byte for every parameter. The reported ~149GB files are not proof of uniformly FP8 storage. As an arithmetic check, 284B one-byte weights alone would exceed the two machines' combined 256GB nominal memory. Exact recipe-weight payloads were not audited here. [Official config](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/raw/main/config.json), [recipe hardware notes](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/docs/hardware-bringup.md).

Two DGX Sparks provide 128GB coherent CPU/GPU memory each, 273GB/s per-system memory bandwidth, Blackwell Tensor Cores and Arm CPUs. Weight shards, runtime state, graphs and host processes all compete for those pools; “unified” does not make memory free or double bandwidth for one rank. The advertised sparse FP4 peak is not a BF16 dense-model throughput measurement. [NVIDIA hardware specifications](https://docs.nvidia.com/dgx/dgx-spark/hardware.html).

TP splits eligible per-layer parameters/computation between ranks, with synchronization cost. It is not one address space across Ethernet, nor a guarantee that every cache/parameter is evenly halved. The official reference contains local-head/group partitioning and an all-reduce for sparse indexer scores, illustrating the communication dependency. [vLLM parallelism definitions](https://docs.vllm.ai/en/latest/configuration/optimization/#parallelism-strategies), [DeepSeek reference code](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/inference/model.py).

ConnectX-7 QSFP ports are rated up to 200Gb/s each, Ethernet-only on Spark. The recipe reports RoCEv2 for TP communication. This supports a low-overhead distributed collective path; the nominal network rate is far below local memory bandwidth and does not establish realized all-reduce latency. Actual channel/rank/topology timings are missing. [NVIDIA networking guide](https://docs.nvidia.com/dgx/dgx-spark/spark-clustering.html), [recipe installation](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/INSTALL.md).

### Attention, context and state

V4 uses trained compressed attention, not post-hoc deletion of arbitrary KV rows. CSA compresses groups then uses learned sparse selection; HCA compresses more aggressively and attends densely over the shorter history. Sliding-window entries preserve local detail. Compression needs unfinished-token buffers as well as completed compressed entries. These are numerical state domains with distinct update and reuse rules. [DeepSeek architecture/cache sections](https://arxiv.org/html/2606.19348v1).

The Flash config alternates compression ratios 4 and 128 after initial local layers; window 128, index top-k 512, maximum positions 1,048,576, YaRN factor 16 and original position range 65,536. The launcher chooses a slightly smaller 1,000,000 ceiling. Position-extension math, learned compression and sparse attention are already part of this model; enabling a generic long-length override does not supply them to another model. [Official config](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/raw/main/config.json), [1M template](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/launch/serve-1m.sh).

The reference compressor retains FP32 KV/score tails, carries overlap windows at ratio 4, applies learned pooling, normalization and rotary transforms, and updates compressed storage only at valid boundaries. The indexer has separate state and scoring. This is why an implementation needs exact typed state and boundary tests; reusing just the visible compressed attention cache is insufficient. The reference also labels some quantization as simulation, so it is not itself proof of the optimized recipe's physical packing. [Reference implementation](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/inference/model.py).

The official paper describes a bounded state pool plus paged compressed history, and discusses disk-backed prefix reuse with tail recomputation/checkpoint tradeoffs. The inspected recipe enables prefix caching but does not demonstrate that its particular run used the paper's disk cache system. Those are distinct evidence levels. [Paper](https://arxiv.org/html/2606.19348v1), [launch](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/launch/serve-1m.sh).

FP8 KV storage can reduce cache bytes and permit more live tokens. Scale policy, attention backend and sensitive layers matter; current vLLM documents per-tensor/per-head calibration and retaining selected layers at native precision. A smaller cache format does not by itself prove lower decode latency, especially when conversion or fallback kernels dominate. [Quantized-cache documentation](https://docs.vllm.ai/en/latest/features/quantization/quantized_kvcache/).

### Serving execution mechanisms

Chunked prefill divides long prompts so bounded prefill work can coexist with decoding. Current vLLM prioritizes pending decodes and fills the remaining token budget with prefills; budget size trades prompt latency against decode interference. This explains the purpose of separate token/sequence ceilings, but does not prove the exact historical binary's scheduler or give a fair policy for us unchanged. [vLLM tuning](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill).

Graph replay reduces host submission overhead by reusing compatible execution structure. Current vLLM distinguishes uniform decode from prefill/mixed batches and dispatches full versus partial graphs accordingly; combined mode consumes extra capture memory and startup time. It still requires backend compatibility and stable resource/shape semantics. [Graph design](https://docs.vllm.ai/en/latest/design/cuda_graphs/).

Prefix caching reuses completed prefix work. Its direct benefit is prefill reduction for repeated prefixes; it does not speed an unrelated query's ongoing decode. [Automatic prefix caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/).

MTP proposes a short continuation and lets the target verify it. Its gain depends on acceptance and target-verification cost; it is not an exemption from target correctness. Current vLLM describes the primary opportunity as memory-bound medium/low-QPS decode and explicitly notes floating-point/batch-shape variations. [Speculative decoding](https://docs.vllm.ai/en/latest/features/speculative_decoding/).

One small, independently composable source change in the later upstream PR removes a per-step GPU-to-CPU position-max query in favor of trusted CPU-side sequence metadata. Decode equivalence and a bounded prefill overestimate are stated explicitly. The lesson is to remove redundant synchronization only with a source/shape proof. The PR also adds model-specific warmup and cache/speculation correctness repairs; it is not merely a flag pack. [PR change inventory](https://github.com/vllm-project/vllm/pull/41834).

Artifact-cache reuse in the recipe's FlashInfer patch accepts an already-present CUBIN only after checksum verification. This is a useful startup/cache mechanism, not evidence of faster steady-state arithmetic. [Patch](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/build/flashinfer_cache.patch).

## What the performance evidence does and does not establish

The result document reports about 37tok/s aggregate at concurrency 1 in its 1M configuration, 98 at concurrency 6/12, and 101 at 24; per-stream rates fall roughly 37→16→8→4. The 256K profile reports about 40 single-stream /150 aggregate, with 32-sequence regression. These are author figures, without accompanying raw benchmark receipts in the inspected copy. The quality probe is LLM-judged, not model numerical parity. [Published results](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/docs/benchmark-results.md).

The probe varies short prompts, requests 128 output tokens by default, temperature 0.7, disables thinking, discards a warmup round and uses non-streaming HTTP. Aggregate throughput divides completed tokens by round wall time; “per-stream tok/s” divides tokens by whole-request latency, including queue/prefill. Token usage falls back to whitespace counting if absent. Errors are counted, but latency statistics use successes and the script can still return success. It records neither streaming TTFT/TPOT nor exact million-token prompt service. Shared prompt beginnings can also hit the enabled prefix cache. [Actual probe](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/bench/throughput.py), [benchmark guidance](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/bench/README.md).

The June30 forum follow-up attributes gradual UMA exhaustion mainly to retained UCX registration-cache regions and proposes `UCX_MEM_MMAP_HOOK_MODE=none` plus `UCX_RCACHE_MAX_UNRELEASED=1024`. It reports a five-concurrent-request A/B, a practical 0.80–0.82 utilization range and clean 512K/1M serving; a >12-hour saturation soak remained pending. Those are author-observed results, not verified here or a general driver diagnosis. The earlier SM120 issue was explicitly not proof of the same SM121 cause. [Revised forum diagnosis](https://forums.developer.nvidia.com/t/guide-deepseek-v4-flash-on-2x-dgx-spark-gb10-reproducible-vllm-serving-recipe-up-to-1m-token-context/374742).

The older recipe uses cache-dropping sidecars; the follow-up suggests swap/sysctl changes. None should become an inference optimization or automatic host mutation in Zerogravity. The portable lesson is to budget and retire transport registrations, host caches, graph pools and device allocations for their actual lifetime. [Historical bring-up](https://github.com/ldm0/deepseek-v4-1m-on-dgx-spark/blob/16dace6/docs/hardware-bringup.md), [forum follow-up](https://forums.developer.nvidia.com/t/guide-deepseek-v4-flash-on-2x-dgx-spark-gb10-reproducible-vllm-serving-recipe-up-to-1m-token-context/374742).

Unresolved reproduction inputs: exact source/model revisions for the June measurements; final image/toolchain/dependency identities; driver/firmware/UCX version; physical per-rank cache bytes; actual input-length distribution; graph/eager coverage; speculation acceptance; streaming latency percentiles; failures/timeouts; long-context quality and >12-hour memory stability. No numeric speedup prediction for Zerogravity follows from this source set.

Arithmetic planning bound: a nominal dense 27B model needs 54GB at BF16, 27GB at one byte, or 13.5GB at 4 bits before scales, unquantized tensors, caches and workspaces. Thus fitting a full 27B model under 5GiB cannot be promised by this recipe; larger hardware, explicitly admitted offload, or a different authorized representation is necessary. Compression/on-demand movement may enable capacity while reducing speed. This is a lower-bound estimate, not a specific checkpoint payload audit.

## Qwen and Gemma4: what actually transfers

Qwen family identity must be explicit. The current official Qwen3.5-27B config has 64 layers, 3 linear-attention layers per full-attention layer, F32 recurrent-state dtype, 4 full-attention KV heads, a 262144 position ceiling, untied embeddings and one MTP layer. Its schema resembles the hybrid family under investigation, but its dimensions/head/source identity are not our 0.8B fixture. Qwen3.8 or another “27B” revision requires a separate exact binding. [Official 27B config](https://huggingface.co/Qwen/Qwen3.5-27B/raw/main/config.json).

Separately checked the already-approved local `Qwen/Qwen3.8-27B@1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0` snapshot. Its 4312B config SHA256 `191e0af232104ed8b65258cf3fb2b842e288008baca7633c11b82a1ac7203aab` matches its manifest and independently sets 64 layers, F32 SSM, an untied head, one MTP layer and no dedicated MTP embeddings. The index lists 15 MTP-named entries. This is source-metadata verification only: no new acquisition, weight-payload authentication, architecture implementation or MTP execution. [Cached manifest](/home/pvl/.cache/abird/zerogravity/models/snapshots/98cea13c169310196c4d8a113765f8fe58ab7a7961f0d1be69212c70dba8015e/manifest.json), [actual config](/home/pvl/.cache/abird/zerogravity/models/snapshots/98cea13c169310196c4d8a113765f8fe58ab7a7961f0d1be69212c70dba8015e/files/config.json), [index](/home/pvl/.cache/abird/zerogravity/models/snapshots/98cea13c169310196c4d8a113765f8fe58ab7a7961f0d1be69212c70dba8015e/files/model.safetensors.index.json).

Gemma4 has its own local/global attention pattern, model-specific windows, proportional rotary behavior, and shared K/V global attention. E2B/E4B also use per-layer embeddings. Its 26B-A4B MoE differs from its dense variants. Those source-defined differences can substantially affect residency, KV bytes and chosen kernels; none may be inferred from the model's display name alone. [Gemma4 model card](https://ai.google.dev/gemma/docs/core/model_card_4).

The official Gemma library exposes KV-sharing patterns separately from attention type. Later layers can reuse specific earlier local/global caches; `k_eq_v` and local/global head dimensions are explicit. A storage planner should allocate for physical producers and shared identities, not sum every logical descriptor as independent storage. The embedding source also has a `[vocab, layers, per_layer_dim]` table, making source-owned bounded row gathering relevant. Exact cache sharing is configuration-dependent, not universal to all Gemma4 variants. [Sharing configuration](https://github.com/google-deepmind/gemma/blob/main/gemma/gm/nn/gemma4/_config.py), [attention/embedding implementation](https://github.com/google-deepmind/gemma/blob/main/gemma/gm/nn/gemma4/_modules.py).

Google's trained Gemma4 MTP drafter shares input embeddings and consumes last-layer target activations; E2B/E4B additionally use clustered vocabulary prediction. Google warns that 26B-A4B batch1 can gain little because verification activates additional experts; higher batches can reuse more expert weights. Therefore a drafter is a candidate stage with measured acceptance and traffic-dependent policy, not a universal multiplier. [Official MTP mechanism and caveat](https://ai.google.dev/gemma/docs/mtp/overview).

### Ranked candidates immediately after parity

Ranking is our inference, with no measured gain claimed. “Immediate” means investigate and implement qualified increments after correctness parity; it does not authorize bypassing the current parity work or adopting another engine.

| Rank | Mechanism / expected useful regime | Qwen / Gemma application | Dependencies, risks and decisive measurement |
|---|---|---|---|
| 1 | Bounded continuous batching + chunked prefill; high impact when single-request decode underuses the device or long prompts block others | Batch genuine hybrid requests through the same operations; choose small prefill quanta while protecting decode and prefill progress | Fresh source/session/state binding per request; exact initialized state ranges; aggregate token/memory admission; age/fairness cap. Compare useful throughput at fixed p95 TTFT/TPOT, not aggregate tok/s alone. Basis: [token-budget scheduler](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill). |
| 2 | Remove hot-path host synchronization and reuse bounded graph/command shapes; fuse only proven compatible adjacent operations | Decode RMS/projections/GDN or attention/head become candidates after device/host timeline identifies repeated launch gaps | Keep original reduction/order contracts or requalify numerical changes; graph memory/shape variants charged before execution; no hidden warmup or late allocations. Compare host gaps, launch counts, real latency. Basis: [graph mechanism](https://docs.vllm.ai/en/latest/design/cuda_graphs/), [metadata synchronization example](https://github.com/vllm-project/vllm/pull/41834). |
| 3 | Layer-aware cache residency and sealed prefix/state reuse; potentially large for long/shared prompts and capacity | Qwen: growing full-attention KV plus exact recurrent snapshots. Gemma: bounded local cache, global history and actual configured sharing; source-owned embedding rows | Restore the full frontier state, not only KV. Copy-on-write independently owned roots; exact source/token/position/profile identity. Test page/window boundaries, branches, restores and missed-prefix behavior. Basis: [hybrid-cache semantics](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/), [Gemma configuration](https://github.com/google-deepmind/gemma/blob/main/gemma/gm/nn/gemma4/_config.py). |
| 4 | Source-bound low-bit weight kernels / selective low-precision KV; capacity prerequisite for larger models, possible bandwidth benefit | Evaluate SM86-supported representation for the exact Qwen/Gemma target; keep sensitive recurrent/norm/cache domains at required precision | New immutable quantized source profile, scales/group/layout validation, physical kernels; distinguish conversion overhead from bandwidth savings. ## Proposed composable stages within the existing Rust engine

This section is design inference constrained by the user's engine/ownership requirements, not a claim that the guide implements our contracts.

1. **Resolve an immutable execution profile.** Authenticate actual weights/config/tokenizer, quantization scheme/scales, position math, model state domains, device capability and kernel ABI. A cached executable or tuned shape is subordinate to this identity. Host/kernel cache hits cannot change it.
2. **Prepare and admit physical resources.** Compute storage from allocation identity/aliasing, active initialized regions and live owners. Reserve source windows, host staging, graph/static buffers, KV pages, recurrent candidates, draft buffers and any transport registrations. Peak overlap during handoff matters. No allocation invisibly moves outside the physical ResourceArbiter.
3. **Choose a bounded fair work unit.** Existing fair workers select admitted decode/prefill chunks; maintain both decode SLO and eventual prefill progress. A batch is a collection of already-authorized per-request attempts. It is not a replacement StateRoot or an issuer of Ready.
4. **Bind actual state and execute the same operation graph.** Each request's immutable input, frontier, source and active physical ranges bind to the prepared storage. Select compatible eager/graph/fused kernels through one mathematical engine. Schedule metadata may remove redundant synchronization only if it is trusted and equivalent to the device input range.
5. **Optional verified prefix restore / draft candidate.** Prefix reuse reconstructs all required domains at an authenticated frontier. Drafting creates disposable candidate state; target verification uses the same engine and target source. No public sampled ID or drafter output gets direct publication authority.
6. **Complete, validate, then publish once.** Original completion/status and session/RootAttempt checks govern target output and accepted state. Preserve predecessor/candidate ownership and exact accepted prefix. Rejected tails retire only after all physical readers/writers complete. Cancellation/unknown completion quarantines complete retained resources.
7. **Retire and account.** Reclaim leases, page references, graphs, source windows and registrations according to actual completion, not logical request disappearance. Cache retention needs a bounded admitted owner and eviction policy. Expose retained versus reusable versus quarantined bytes separately.

Composable interfaces should describe capability (shape/layout/state effects, memory cost, completion obligation), not embed an opaque external engine or add a second traversal with its own token authority. A later RDMA implementation could be a transport stage with physical tickets and rank-failure quarantine; it is unnecessary for the first Qwen/Gemma improvements.

## Qualification and benchmark requirements

These are proposed acceptance gates, not executed results:

- **Establish the baseline first:** complete actual natural-feedback vLLM parity at the intended source/model/precision. Existing forced five-phase diagnostics alone do not demonstrate natural generation or full serving parity. Do not relabel them because another project's benchmark looks plausible.
- **Numerical closure:** exact source windows and weights; positions; per-operation and layer boundaries; full logits/greedy tie rules; all model-defined active canonical states; unchanged predecessor carry; arbitrary admitted chunk splits and continuation lengths. The current Qwen fixture's domain count cannot be copied to a different Qwen or Gemma model.
- **Hybrid/cache closure:** active noncontiguous strides and page mappings; allocated versus logical alias counts; local-window wrap; recurrent and convolution histories; cache-hit intersection across domain types; shared-KV producer identity; partial final blocks; copy-on-write branches/restores; stale/source-mismatched/corrupt cache refusal; no future padding read as expected data.
- **Graphs/fusion/batching:** same inputs at each admitted shape/batch composition, zero/full/mixed batches, capture boundary and fallback, numerical differences caused by changed reduction shape, bounded graph retention, source changes, cancellation before/after enqueue and unknown completion. Fairness includes long-prefill progress under continuing decode arrivals.
- **Speculation:** zero/all/partial acceptance, first rejection, EOS and stop boundaries, target-only output equivalence for the claimed sampler, rejected-tail state disposal, prompt/draft block protection, source/activation/drafter binding. Probability-distribution preservation does not automatically mean identical seeded traces under different floating-point batching.
- **Physical lifecycle:** cold/mid-load refusal, partial uploads, real cancel points, multiple requests, failed status/fence/transport, unknown completion, root publication races, final retained-memory accounting. No cache or graph ownership cycle may hide outstanding work from teardown.
- **Performance matrix:** fixed tokenizer/source/quantization, exact input/output token counts; cold and warm prefix separately; short established profiles before long contexts; prompt lengths increasing to the genuinely admitted limit; concurrency and arrival-rate sweeps; mixed short/long traffic and cancellation. Record TTFT, TPOT/ITL, p50/p95/p99, useful output throughput, errors/timeouts and SLO attainment.
- **Cost and stability:** measured device/host peaks and unique allocations, KV occupancy, graph pools, source transfer bytes, preemption/recompute, draft acceptance/cost, kernel/host gaps, cache hit rate and resident/quarantine bytes. Separate startup/JIT from steady-state. Run enough repeated/soak work to catch per-request retention; never hide failed requests from latency/throughput reports.
- **Causal comparison:** change one mechanism at a time against the unchanged same-source reference, then measure combinations. Publish workload/config/versions with actual results; no unmeasured product of individual speedups. Complete repository checks and relevant real state/cancellation/physical gates remain mandatory for implementation acceptance.
